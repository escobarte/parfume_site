# Бэкапы — операционная инструкция

Фактическая инфраструктура — TopHost VPS + Coolify + Cloudflare DNS (не Hetzner/R2, как в `docs/PLAN.md` §9 — см. `docs/STATE.md` → раздел «Фаза 9»). Этот файл писан под неё.

## Что бэкапится и как

| Что | Механизм | Где хранится | Периодичность | Ротация |
|---|---|---|---|---|
| **PostgreSQL** (заказы, товары, страницы, пользователи админки, все коллекции) | Встроенные Backups сервиса Postgres в Coolify | Локальный диск VPS — S3/R2 в проекте не подключён (см. `docs/STATE.md` → «Фаза 9»), это временный минимум | по расписанию cron, рекомендация `0 3 * * *` (03:00 каждую ночь) | retention 30 снапшотов (настройка Coolify) |
| **Медиа** (`/app/media`, фото товаров) | `scripts/backup-media.sh`, запускается cron'ом на самом VPS | Отдельная директория на VPS, вне докерных volume'ов — по умолчанию `/opt/backups/media` | ежедневно, рекомендация cron `0 4 * * *` (через час после бэкапа БД) | N последних архивов, по умолчанию **14** (`RETENTION`) |

Оба бэкапа сейчас живут на одном и том же VPS, что и прод — это осознанный временный риск (единая точка отказа диска/сервера), а не целевое состояние. Закрывается либо подключением Cloudflare R2 (Postgres → Coolify S3 Storage) и/или внешнего SSH-хоста под медиа (закомментированный rsync-блок в `scripts/backup-media.sh`) — оба пункта требуют решения и доступов владельца, код к ним уже готов.

## Настройка бэкапа Postgres (Coolify)

1. Coolify → проект → сервис **Postgres** → вкладка **Backups**.
2. **Schedule** (cron-выражение в самой Coolify): `0 3 * * *`.
3. **Retention**: 30.
4. Хранилище: пока **Local** (диск VPS) — так и должно быть, пока не подключён S3-совместимый бакет. Когда появится Cloudflare R2 (или другой S3-совместимый провайдер): Coolify → **Settings → S3 Storages** → добавить бакет → в настройках бэкапа Postgres выбрать его вместо Local.
5. Сохранить настройки, затем либо дождаться первого автозапуска по расписанию, либо нажать **Run** вручную сразу — и проверить, что в списке бэкапов появился новый файл дампа с ненулевым размером.

## Настройка бэкапа медиа (`scripts/backup-media.sh`)

Скрипт уже в репозитории. Он ничего не запускает сам — cron-запись на сервере ставит владелец.

### Что делает скрипт (коротко)

1. Находит на хосте директорию, которую Docker примонтировал в контейнер приложения на `/app/media` (Coolify persistent volume) — **динамически**, через `docker inspect` по всем запущенным контейнерам. Id/имя контейнера не хардкодится: Coolify пересоздаёт контейнер приложения на каждом деплое с новым id.
2. Архивирует найденную директорию в `.tar.gz` в `/opt/backups/media` (переопределяется `BACKUP_DIR`).
3. Хранит последние `N` архивов (по умолчанию 14, `RETENTION`), старые удаляет.
4. Логирует в `$BACKUP_DIR/backup-media.log` и в stdout.
5. При любой ошибке (volume не найден, `tar` упал, неверно настроен `BACKUP_DIR`) — ненулевой exit code, ротация не запускается, ничего не удаляется.

Полное описание параметров — в комментарии в шапке самого файла.

### Установка на сервере (выполняет владелец)

```bash
# Директория под архивы, вне докерных volume'ов
sudo mkdir -p /opt/backups/media

# Скрипт уже исполняемый в git, но на всякий случай:
chmod +x /path/to/repo/scripts/backup-media.sh
```

`/path/to/repo` — путь к копии репозитория на самом VPS. Coolify не гарантирует стабильный путь билд-контекста между деплоями (пересобирает в новую директорию), поэтому под cron-задачу надёжнее держать отдельный лёгкий чекаут (`git clone`, только для этого скрипта, обновляется вручную при изменении скрипта), а не указывать в cron путь внутрь рабочей директории Coolify.

### Cron-запись

От пользователя с доступом к Docker CLI (root, либо член группы `docker` — скрипту нужны `docker ps`/`docker inspect`):

```cron
0 4 * * * /usr/bin/env bash /path/to/repo/scripts/backup-media.sh >> /opt/backups/media/cron.log 2>&1
```

С нестандартными параметрами (директория/ротация):

```cron
0 4 * * * BACKUP_DIR=/opt/backups/media RETENTION=14 /usr/bin/env bash /path/to/repo/scripts/backup-media.sh >> /opt/backups/media/cron.log 2>&1
```

Поставить: `crontab -e` (для root — `sudo crontab -e`), вставить строку, сохранить.

### Как проверить, что бэкап реально создался

```bash
# Список архивов, самый свежий должен быть с недавней меткой времени
ls -lh /opt/backups/media/

# Последние строки лога — там же итог: "готово: ..." и "бэкап медиа завершён успешно"
tail -20 /opt/backups/media/backup-media.log

# Архив не пустой и не битый — список файлов внутри
tar -tzf /opt/backups/media/media-<последний-таймстамп>.tar.gz | head

# Ручной прогон и проверка кода возврата
/usr/bin/env bash /path/to/repo/scripts/backup-media.sh; echo "exit code: $?"
```

Ненулевой `exit code` или отсутствие новых файлов в `ls` — сигнал разбираться (в первую очередь смотреть `backup-media.log`, там всегда есть строка с точной причиной).

## Внешнее хранилище медиа

Сейчас его нет — Cloudflare R2 в проекте не подключался (см. `docs/STATE.md` → «Фаза 9», «Организационный контекст»). В `scripts/backup-media.sh` есть готовый, но закомментированный блок `rsync` по SSH-ключу — когда появится внешний SSH-доступный хост, раскомментировать и подставить `REMOTE_USER`/`REMOTE_HOST`/`REMOTE_PATH` (инструкция — прямо в комментарии над блоком).

## Проверка восстановлением

Бэкап, который ни разу не разворачивали, бэкапом не считается. Пошаговая инструкция — `docs/restore-drill.md`. Пройти вживую один раз после первой настройки расписания, дальше — раз в месяц (см. `docs/STATE.md` → «Дальше — фаза 10»).
