# Restore drill — проверка бэкапов восстановлением

Бэкап, который ни разу не разворачивали, бэкапом не считается (`PLAN.md` §11.2). Этот файл — пошаговая тренировка: скачать последний прод-дамп Postgres, поднять его в изолированном Postgres в WSL, убедиться что данные реально читаются, и (отдельно, с предупреждениями) — как восстановить медиа-архив обратно в volume на проде.

**Кто выполняет.** Разделы 1–3 (скачать дамп, поднять локально, проверить) — безопасны, можно выполнять кому угодно, включая Claude Code по явной просьбе (только read-only операции на localhost). Раздел 4 (восстановление медиа на проде) трогает боевой сервер — у Claude Code нет `ssh`-доступа туда (`CLAUDE.md`, запрет 2), эти команды выполняет владелец сам. Раздел 5 — обязательно прочитать до раздела 4.

**Периодичность.** Пройти вживую один раз сразу после первой настройки расписания бэкапов Postgres в Coolify (см. `docs/backup.md`), дальше — раз в месяц, поставить себе напоминание.

---

## 1. Скачать последний дамп Postgres из Coolify

Бэкапы сейчас хранятся локально на диске VPS (S3/R2 не подключён, см. `docs/backup.md`).

**Через панель Coolify (проще всего):**

1. Coolify → проект → сервис **Postgres** → вкладка **Backups**.
2. В списке снапшотов — самый свежий по дате. Нажать **Download**.
3. Файл сохранится на компьютер владельца — скопировать/перенести его в WSL (например, в `/mnt/c/Users/<...>/Downloads/`, оттуда скопировать в рабочую директорию для дрелла):

```bash
mkdir -p ~/restore-drill
cp "/mnt/c/Users/<user>/Downloads/<файл-дампа>" ~/restore-drill/
cd ~/restore-drill
```

**Если UI-скачивание недоступно** — через Coolify Terminal (в панели, вкладка Terminal у сервиса Postgres или у самого сервера), владелец сам находит файл дампа на диске VPS (типовой путь у Coolify — `/data/coolify/backups/...` или указанный в настройках Backups) и переносит его на свою машину любым штатным способом панели. Claude Code эту часть не выполняет — нет доступа к серверу.

**Определить формат дампа** (Coolify обычно делает `pg_dump` в custom-формате, но лучше проверить, а не предполагать):

```bash
file ~/restore-drill/<файл-дампа>
```

- Начинается с `PGDMP` / определяется как `PostgreSQL custom database dump` → восстанавливать `pg_restore` (раздел 2, вариант A).
- Обычный текст, начинается с `--` (SQL-комментарии) → восстанавливать `psql -f` (раздел 2, вариант B).

## 2. Поднять дамп в изолированном Postgres в WSL

**Важно: не восстанавливать поверх рабочей dev-БД проекта** (`parfume_pgdata`, том из `docker-compose.dev.yml`, порт 5432) — если что-то пойдёт не так, не хочется терять локальные dev-данные. Дрелл поднимает **отдельный, временный** контейнер Postgres (тот же образ, что использует проект — `postgres:17-alpine`, см. `docker-compose.dev.yml`), на отдельном порту.

```bash
docker run -d --name parfume_restore_drill \
  -e POSTGRES_USER=parfume \
  -e POSTGRES_PASSWORD=parfume \
  -e POSTGRES_DB=parfume_restore \
  -p 5433:5432 \
  postgres:17-alpine

# Дождаться готовности
until docker exec parfume_restore_drill pg_isready -U parfume -d parfume_restore >/dev/null 2>&1; do
  sleep 1
done
echo "Postgres готов"
```

**Вариант A — custom-формат (`pg_restore`):**

```bash
docker exec -i parfume_restore_drill \
  pg_restore --no-owner --no-acl -U parfume -d parfume_restore \
  < ~/restore-drill/<файл-дампа>
```

**Вариант B — plain SQL (`psql`):**

```bash
docker exec -i parfume_restore_drill \
  psql -U parfume -d parfume_restore \
  < ~/restore-drill/<файл-дампа>
```

Обе команды могут напечатать предупреждения про роли/владельцев (`role "coolify" does not exist` и т.п.) — это ожидаемо (дамп снят от другого пользователя БД), не блокер: `--no-owner --no-acl` у `pg_restore` как раз для этого случая. Если `psql`-вариант ругается на `GRANT`/`ALTER OWNER` построчно — тоже не критично, данные восстанавливаются, ошибки только на правах доступа.

## 3. Проверить, что данные реально читаются

### Быстрая проверка — прямые SQL-запросы

```bash
docker exec -it parfume_restore_drill psql -U parfume -d parfume_restore
```

Внутри `psql`:

```sql
-- Сначала посмотреть реальные имена колонок (могут отличаться от предположений ниже)
\d products
\d orders
\d pages

-- Количество записей по ключевым таблицам — должно быть не 0
SELECT count(*) FROM products;
SELECT count(*) FROM orders;
SELECT count(*) FROM pages;
SELECT count(*) FROM brands;

-- Реальные заказы, не просто count — видно, что это настоящие боевые данные
SELECT id, status, total, created_at FROM orders ORDER BY created_at DESC LIMIT 5;

-- Товары с ценами (денормализованные min/max, см. docs/GOTCHAS.md)
SELECT id, slug, min_price, max_price, in_stock FROM products LIMIT 5;

-- Статические страницы (О нас/Доставка/Возврат/Контакты)
SELECT id, slug FROM pages;
```

Если `\d products` показывает другие имена колонок (например, `min_price` на самом деле называется иначе) — использовать реальные имена, а не строку выше буквально; денормализация полей описана в `docs/CHANGELOG.md`/`docs/GOTCHAS.md`, но точные имена колонок в БД — источник истины `\d`.

Пустой `count(*)` на любой из ключевых таблиц (`products`/`orders`/`pages`) — сигнал, что дамп восстановился не полностью, дальше идти нельзя, разбираться сначала с этим.

### Полная проверка — через локальную админку Payload

Более надёжная проверка (не только «строки в таблице есть», а «Payload реально может их прочитать и отрендерить»): поднять сам проект против восстановленной БД.

```bash
cd ~/projects/parfume_site
cross-env DATABASE_URI="postgres://parfume:parfume@localhost:5433/parfume_restore" \
  PORT=3010 pnpm dev
```

Открыть `http://localhost:3010/admin`, залогиниться существующим прод-админом (учётные данные знает только владелец — `admin.monflacon@gmail.com`, см. `docs/STATE.md` → «Фаза 9»). Проверить:

- **`/admin/collections/orders`** — список заказов не пуст, открыть один — видны реальные `customer`/`items`/`status`, не пустые поля.
- **`/admin/collections/products`** — список товаров совпадает по количеству с тем, что ожидается на проде на момент снятия дампа (на 2026-08-20 — 12 демо-товаров, дальше будет расти).
- **`/admin/collections/pages`** — четыре страницы (О нас/Доставка/Возврат/Контакты) на месте, с содержимым на всех локалях.
- Опционально — открыть витрину `http://localhost:3010/ro/catalog`: товары должны отрендериться (текст, цены, slug'и) корректно; **фото не появятся** — этот дрелл проверяет только Postgres, файлы медиа не восстанавливались локально (см. раздел 4, там про сам медиа-архив, отдельная процедура и только на проде).

Остановить дев-сервер (`Ctrl+C`) после проверки.

### Уборка временного контейнера

```bash
docker rm -f parfume_restore_drill
```

Дамп в `~/restore-drill/` можно оставить до следующего дрелла или удалить — он не секретнее, чем сам прод (реальные данные заказов с телефонами клиентов), не оставлять на общедоступном диске/в облаке без необходимости.

## 4. Восстановить медиа из архива обратно в volume на проде

Выполняет **владелец**, на самом VPS (Coolify Terminal или прямой доступ к серверу) — не Claude Code.

### 4.1 Найти путь тома на хосте (тот же приём, что в `scripts/backup-media.sh`)

```bash
for cid in $(docker ps -q); do
  src=$(docker inspect -f '{{ range .Mounts }}{{ if eq .Destination "/app/media" }}{{ .Source }}{{ end }}{{ end }}' "$cid")
  [ -n "$src" ] && echo "$cid -> $src"
done
```

Записать полученный путь (`MEDIA_HOST_PATH`) — понадобится ниже.

### 4.2 Сделать страховочную копию текущего состояния (даже если оно "неправильное")

```bash
MEDIA_HOST_PATH="<путь из шага 4.1>"
sudo tar -czf /opt/backups/media/pre-restore-safety-$(date +%Y%m%d-%H%M%S).tar.gz \
  -C "$(dirname "$MEDIA_HOST_PATH")" "$(basename "$MEDIA_HOST_PATH")"
```

Так, если восстановление окажется ошибкой (не тот архив, не то время), есть куда откатиться.

### 4.3 Остановить приложение

Coolify → приложение → **Stop**. Обязательно — см. предупреждения в разделе 5.

### 4.4 Заменить содержимое volume на данные из архива

```bash
sudo rm -rf "${MEDIA_HOST_PATH:?}"/*
sudo tar -xzf /opt/backups/media/media-<таймстамп-нужного-архива>.tar.gz \
  -C "$(dirname "$MEDIA_HOST_PATH")"
```

`${MEDIA_HOST_PATH:?}` — намеренная защита от `rm -rf /*`, если переменная вдруг окажется пустой (bash упадёт с ошибкой вместо удаления неизвестно чего).

### 4.5 Запустить приложение обратно

Coolify → приложение → **Start** (или **Restart**, если Stop не полностью остановил).

### 4.6 Проверить

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://monflacon.md/
curl -s -o /dev/null -w '%{http_code}\n' https://monflacon.md/api/media/file/<известное-имя-файла>
```

Второй `curl` — на файл, который точно должен существовать (взять slug/имя любого товара с фото из `/admin`). Оба должны отдать `200`. Открыть `/catalog` в браузере — фото товаров отображаются.

## 5. Чего нельзя делать при восстановлении на проде

- **Не восстанавливать дамп поверх боевой БД без остановки приложения.** Пока Postgres принимает запись `pg_restore`/`psql`, приложение продолжает писать (новые заказы, ревалидация кэша) — получится смесь старых и новых данных, возможна порча последовательностей (`id`) и дублирование. Останавливать приложение **до** восстановления БД, не только медиа.
- **Не восстанавливать медиа-volume без остановки контейнера приложения.** Payload может параллельно писать новые файлы во время `tar -x`/`rm -rf`, тогда БД будет знать о файле, которого на диске уже/ещё нет (или наоборот) — рассинхрон, что и так уже случалось с кэшем (`docs/GOTCHAS.md`).
- **Не тренироваться на боевом Postgres «просто посмотреть».** Тренировка (разделы 1–3) — всегда в изолированном временном контейнере, как описано выше. Боевой Postgres трогается только при реальном восстановлении после инцидента.
- **Не выполнять restore без явного «да» владельца.** Это деструктивная операция (`rm -rf` содержимого volume, перезапись БД) — `CLAUDE.md`, запрет 4: только после явного согласия, не по инициативе Claude Code.
- **Не удалять старый/текущий архив или дамп до подтверждения, что восстановленная версия рабочая.** Если restore пошёл не так — должно быть куда откатываться (шаг 4.2 не пропускать).
- **Не восстанавливать в часы пикового трафика без предупреждения.** На время restore (БД + медиа) сайт будет недоступен или отдавать неполные данные — предупредить заранее, если есть кому.
- **Claude Code не выполняет ничего из раздела 4 самостоятельно** — нет `ssh`-доступа к серверу (`CLAUDE.md`, запрет 2). Этот раздел — инструкция для владельца, не задача для автоматического выполнения.
