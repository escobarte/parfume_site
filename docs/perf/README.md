## Осознанно НЕ исправлено (зафиксировано, не забыто)

- **Контраст бренд-строки на главной** (`BrandStrip.tsx`, `#9AA6B4` на белом, тот же принцип — 2.47 вместо 4.5). Держит accessibility на 95–96 вместо 100, но выше порога ≥95 из PLAN.md. **Не тронуто**, потому что цвет — не случайный выбор реализации, а буквальное значение из `docs/WIREFRAMES.md` §5: «названия брендов uppercase 12px, tracking .26em, `#9AA6B4`». Менять зафиксированный в вайрфреймах хекс-код в одностороннем порядке — не моё решение; если владелец хочет привести и этот элемент к AAA/AA, нужна правка WIREFRAMES.md, а не только кода.
- **`bf-cache` (back/forward cache) отключён** — `Cache-Control: no-store` на HTML-документе, следствие `dynamic = 'force-dynamic'` в `[locale]/layout.tsx` (задокументированное решение фазы 3: шапка/футер тянут live-данные из Payload, полный кэш маршрутов — фаза 7, когда появится прод-инфраструктура с CDN). Both failure reasons сам Lighthouse помечает `Not actionable` на уровне страницы.
- **Фантомный self-redirect на первом заходе.** Реальный браузер (Chromium, Playwright) на самом первом обращении к любой локализованной странице без `NEXT_LOCALE`-cookie иногда получает `307` на тот же самый URL (проверено вживую через `page.goto()` + `redirectedFrom()`), что стоит Lighthouse ~500–600мс на `redirects`/`document-latency-insight`. Через `curl` (с любыми имитирующими браузер заголовками — `Accept-Language`, `Sec-Fetch-*`) не воспроизводится ни разу — похоже на особенность обработки первого захода в next-intl middleware (`syncCookie`) именно в браузерном сценарии. Не голая теория: подтверждено дважды независимо (Lighthouse и отдельный Playwright-скрипт), но не разобрано до основной причины — это стоит времени, несоразмерного объёму фазы 7, и это разовая стоимость только для первого визита конкретного браузера (при рендере на сервере Cache невозможен по определению — при каждом заходе решение принимается заново, но повторные заходы с уже выставленной cookie не показывают этот эффект). Не блокирует достижение порогов ≥90/≥95 — итоговые баллы уже учитывают этот эффект.

## Методология

- `--throttling-method=devtools` — реальный CPU/network throttling через CDP, а не `simulate` (Lantern-предсказание по графу зависимостей). На localhost `simulate` даёт заметно завышенные (пессимистичные) LCP-оценки — до 3.7с против фактических 2.1–2.3с при devtools-throttling на тех же страницах; `devtools` ближе к тому, что увидит реальный пользователь.
- Тестировалась прод-сборка через `pnpm build && pnpm start`, не dev-режим (dev считает Lighthouse-проверку нерепрезентативной из-за HMR/dev-инструментария).
- **Локальная особенность**, не влияющая на прод: `next.config.ts` задаёт `output: 'standalone'` для Docker (см. `Dockerfile`) — при локальном тестировании через `pnpm start` Next печатает предупреждение «does not work with standalone configuration», но фактически обслуживает и код, и локальные медиафайлы Payload корректно (проверено отдельно). Настоящий `.next/standalone/server.js` рассчитан на запуск из скопированной по Dockerfile-схеме директории (`public/` + `.next/static` рядом) — там же, где и продовское S3/R2-хранилище медиа, а не локальный `media/` каталог дев-окружения; смешивать эти два сценария на одной машине без такого копирования не имеет смысла, поэтому раздел «Аудит производительности» прогонялся через обычный прод-режим (`pnpm start`), а не имитацию Docker-раскладки.
