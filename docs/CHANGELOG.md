Причина правки (со слов владельца): пустое описание на ru/en выглядит как недоделанный сайт, дубль хотя бы читается и явно сигнализирует «надо перевести».   - Порядок операций в `applyProducts.ts` теперь жёсткий: посчитать пустые локали → основной create/update → дописать дубли. Иначе не работает вовсе — см. «Заметки».

Показывается только когда дубль реально куда-то лёг (N > 0), одинаково в dry-run и боевом прогоне. Заголовочная строка формата тоже уточнена: `(описание: одна колонка на все языки)` вместо прежнего `(описание: выбранная локаль)`, которое перестало быть правдой.
  - Формат переводов (`handle,locale,description`) не тронут — он точечный, локаль указана в каждой строке явно, дублирование к нему не применяется (проверено отдельно).

## [2026-08-22] Прод-баг — EACCES при загрузке в Media (persistent volume /app/media) — постоянный фикс

- Сделано: postmortem-фикс бага, найденного владельцем на проде (первая настоящая загрузка фото в Media после деплоя фазы 9 — демо-данные до этого заливались CSV-импортом без фото). Диагностика проведена и подтверждена владельцем на VPS до этой сессии (не перепроверял, задача была только в постоянном фиксе): Coolify монтирует persistent volume в `/app/media`, точка монтирования создаётся Docker'ом от root ПОСЛЕ сборки образа — build-time `chown nextjs:nodejs /app` в Dockerfile её физически не может закрыть, монтирование перезатирает владельца обратно на `root:root` при каждом старте контейнера. Симптом — `400 There was a problem while uploading the file`, в логах `EACCES: permission denied, open 'media/<файл>.jpg'`. Временный ручной фикс владельца (`chown -R` через `docker exec -u root`) подтвердил диагноз, но слетает при каждом пересоздании контейнера.
  - `docker-entrypoint.sh` — `USER nextjs` убран из Dockerfile (сохранён явный поясняющий комментарий на его месте — не убирать обратно не подумав), контейнер стартует под root; entrypoint при `id -u = 0` чинит `mkdir -p`/`chown -R nextjs:nodejs /app/media`, затем сбрасывает привилегии на nextjs через `setpriv --reuid=nextjs --regid=nodejs --init-groups --no-new-privs` (execve, не подпроцесс) и рекурсивно перезапускает себя тем же путём — второй проход уже видит непривилегированный uid и идёт по прежней ветке (`payload migrate` → `exec "$@"`). `setpriv` — из `util-linux`, уже есть в базовом образе `node:22-bookworm-slim`, доустанавливать `gosu`/`su-exec` не понадобилось. Сам процесс приложения (`node server.js`) в итоге работает строго под `nextjs` (uid 1001), не под root ни секунды — требование безопасности из промпта выполнено буквально, не обходной путь.
  - Идемпотентно по конструкции — тот же принцип, что уже проверен трижды для автомиграций (см. запись 2026-08-18): контейнер получает root при каждом старте, ветка chown/drop отрабатывает каждый раз одинаково, повторный `chown -R` на уже верных правах — no-op.
- Файлы: `docker-entrypoint.sh`, `Dockerfile`, `docs/GOTCHAS.md` (дополнена существующая запись «Non-root `nextjs`…», не заведён дубль-раздел).
- Зависимости: нет (`setpriv` — часть `util-linux`, уже в базовом образе).
- Ждёт владельца: 👁 задеплоить этот фикс на прод (ветка `phase_8.0`, мерж/деплой — вручную, эта сессия ветку не трогала) и подтвердить живой загрузкой фото через `/admin/catalog-import`, что `EACCES` больше не воспроизводится на реальном VPS (локально проверено эмуляцией того же сценария — root-владелец volume при первом монтировании — но не на самом VPS, доступа нет).
- Заметки: `pnpm tsc`/`pnpm lint` чисто (правки только в `Dockerfile`/`docker-entrypoint.sh`, TS-код не тронут). Живая проверка — полная сборка `docker build` из текущего Dockerfile, контейнер поднят на сети `docker-compose.dev.yml` (тот же Postgres, что и dev) с намеренно root-владельческим volume (Docker создаёт новые volume от root — воспроизводит прод-сценарий монтирования без доступа к самому VPS): лог показал точную последовательность root → chown → drop privileges → migrate → start; `/app/media` после старта — `nextjs:nodejs 755`; `/proc/1/status` работающего процесса — `Uid: 1001` (не 0); реальная загрузка файла через Payload Local API (валидный JPEG, сгенерированный `sharp`) прошла успешно, созданы все размеры (thumb/card/full) — именно та операция, что раньше падала `EACCES`; 4 рестарта того же контейнера подряд — без единой ошибки, `exitcode 0` каждый раз. Тестовый контейнер/volume/образ удалены после проверки, dev-Postgres не затронут (12 демо-товаров на месте).
