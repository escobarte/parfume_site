>

## Схема и база

- **Схема — только через миграции, не через push.** `push: false`, папка `src/migrations`. Изменил схему → `pnpm migrate:create <имя>` + `pnpm migrate`. На проде миграции прогоняются САМИ при каждом старте контейнера (`docker-entrypoint.sh`, см. ниже) — ручной pre-deploy шаг в Coolify не нужен.
- **Standalone-образ (`output: 'standalone'`) не тащит ни CLI `payload`, ни `src/` — `payload migrate` внутри готового контейнера падает `MODULE_NOT_FOUND`.** Next-трассировщик (`@vercel/nft`) копирует в `.next/standalone/node_modules` только то, что реально импортирует `server.js` — бинарник `payload` (`node_modules/.bin/payload` → `payload/bin.js`) в этот граф не попадает вообще (это отдельная точка входа, не часть рантайма Next), и физически отсутствует в образе (ни как файл, ни даже как pnpm-симлинк верхнего уровня — пакет `payload` внутри `.pnpm/`-хранилища физически есть, но без симлинка `node_modules/payload` на него, потому что ничего в трассируемом графе не требует его напрямую). Аналогично отсутствует и `src/payload.config.ts` со всеми коллекциями/миграциями — standalone держит только скомпилированный вывод для Next, не сырые исходники. Решение (Dockerfile, стадия `runner`): отдельная `prod-deps` стадия (`pnpm install --prod --frozen-lockfile`, полноценные pnpm-симлинки) копируется поверх урезанного standalone-среза `node_modules` (строгое надмножество тех же версий по тому же lock-файлу — серверу не мешает); `src/` и `tsconfig.json` копируются из `build`-стадии целиком; `PAYLOAD_CONFIG_PATH=/app/src/payload.config.ts` выставлен явно переменной окружения, чтобы CLI не полагался на эвристику поиска конфига через `tsconfig.json`/`@payload-config`-алиас в непривычном контейнерном `cwd`.
- **Non-root `nextjs` (создан `useradd --system`, без `-m`) не может писать в `/app`.** `WORKDIR /app` создаётся ещё от root ДО `useradd`, и без явного `chown` остаётся `root:root` — любой рантайм-`mkdir` прямо под `/app` (например, `pnpm seed`/`scripts/import.ts` кладут временные файлы в `.seed-tmp/`) падает `EACCES`. Тот же класс проблемы — у `nextjs` вообще нет домашней директории (`/home/nextjs` не существует), из-за чего `pnpm`/corepack не может создать кэш при первом вызове (`EACCES: mkdir '/home/nextjs/.cache/node/corepack/v1'`) — **`pnpm <script>` внутри этого контейнера не работает вообще**, не только миграции. Решение: `chown nextjs:nodejs /app` сразу после `useradd` (Dockerfile) закрывает mkdir-под-/app; сам corepack не чинили (не понадобилось) — вместо `pnpm seed`/`pnpm import` внутри контейнера используется прямой вызов бинарника: `./node_modules/.bin/tsx scripts/seed.ts` (шим уже исполняемый, node.js его напрямую не запустить — `node node_modules/.bin/tsx ...` падает `SyntaxError`, шим сам себе шебанг `#!/bin/sh`, запускать надо как исполняемый файл, не как аргумент `node`).
  **Продолжение той же ловушки, пойманное уже на проде (2026-08-22): persistent volume Coolify поверх `/app/media` возвращает владельца этой ОДНОЙ директории обратно на `root:root`, даже если весь остальной `/app` внутри образа честно принадлежит `nextjs:nodejs`.** Точка монтирования создаётся Docker'ом при старте контейнера — то есть ПОСЛЕ сборки образа и ПОСЛЕ build-time `chown nextjs:nodejs /app` выше, поэтому та строчка её физически не может закрыть: chown из Dockerfile применяется один раз при сборке слоя, а монтирование volume перезатирает метаданные владельца заново на каждом старте контейнера. Симптом — любая загрузка в Media (кнопка «Загрузить архив» на `/admin/catalog-import`, обычная загрузка файла в админке) падает `400 There was a problem while uploading the file`, в логах контейнера — `EACCES: permission denied, open 'media/<имя>.jpg'`. На демо-данных не ловилось: товары фазы 3–8 заливались CSV-импортом вообще без фото (см. `docs/STATE.md`), первая настоящая загрузка фото случилась только 2026-08-22 на проде. Диагностировано на VPS вручную (`docker exec <app> ls -la /app` — все каталоги `nextjs nodejs`, `media` один `root root`) и подтверждено временным `docker exec -u root <app> chown -R 1001:1001 /app/media` (загрузка сразу заработала, но права слетают заново при пересоздании контейнера — не постоянный фикс). **Постоянное решение (`docker-entrypoint.sh` + `Dockerfile`):** `USER nextjs` из Dockerfile снят намеренно (см. комментарий там же) — контейнер стартует под root, `docker-entrypoint.sh` при виде `id -u = 0` чинит `mkdir -p`/`chown -R nextjs:nodejs /app/media`, затем СРАЗУ сбрасывает привилегии через `setpriv --reuid=nextjs --regid=nodejs --init-groups --no-new-privs` (execve на тот же PID, не подпроцесс) и рекурсивно перезапускает сам себя тем же путём — второй проход уже видит `id -u ≠ 0` и идёт по прежней ветке (миграции → `exec "$@"`). `setpriv` — из `util-linux`, в `node:22-bookworm-slim` уже есть из коробки, доустанавливать `gosu`/`su-exec` не пришлось. Идемпотентно по конструкции: контейнер получает root при КАЖДОМ старте (то же самое родительское условие, что и раньше), поэтому ветка отрабатывает на каждом рестарте одинаково — `mkdir -p`/`chown -R` на уже верных правах молча no-op. Проверено локально (не на VPS — доступа нет): собранный образ, volume нарочно создан пустым (Docker создаёт новые volume от root, воспроизводит прод-сценарий), контейнер поднят на сети `docker-compose.dev.yml` — лог показал root→chown→drop→migrate→start, `/app/media` после старта `nextjs:nodejs`, PID 1 (`/proc/1/status`) — uid 1001, не 0, реальная загрузка файла через Payload Local API прошла (созданы все размеры), 4 рестарта подряд — без единой ошибки.
- **`sharp`/libvips падает `SIGSEGV` (exit 139) на SVG с `<text>`, если в образе нет `fontconfig`.** `node:22-bookworm-slim` не ставит шрифты/fontconfig по умолчанию. Ловится только на `scripts/seed.ts`/`seed-load.ts` — их `makePlaceholder()` рендерит SVG-плейсхолдер с текстом бренда через `sharp`; реальный прод-путь (`scripts/import.ts`, загрузка настоящих фото через `/admin`) текст в SVG не рендерит вообще и этой ветки кода не касается — **не блокер запуска**, чинить только если реально понадобится гонять `pnpm seed`/`seed:load` внутри задеплоенного контейнера (сейчас не требуется, наполнение — через CSV-импорт настоящих фото).
- **`payload migrate:create` интерактивен и вешается в headless.** CLI спрашивает «created or renamed» через raw-mode UI, который молча глотает ввод через обычный pipe. Решение — `pty.openpty()` + скрипт, отвечающий `\r` при появлении вопроса. **Рабочий рецепт без node-pty (фаза 11.1, задача 3):** утилита `script` из `util-linux` (уже есть в образе/WSL) сама выделяет псевдо-tty — `timeout 30 script -qc "pnpm migrate:create <имя>" /dev/null <<< $'\r\r\r\r\r\r\r\r'` (несколько `\r` на случай нескольких вопросов подряд). Поймано на практике: перенос поля `productCategory` внутрь нового `row` в `Products.ts` заставил CLI спросить «created or renamed» (голый `pnpm migrate:create` без tty висел до `timeout`, миграция не создавалась вообще) — с `script` тот же вызов прошёл на первой попытке.
- **«Compare-and-set» через Payload Local API — `payload.update({ where, data })` (bulk-вариант, не по `id`), не read-then-write.** Одноразовые промокоды (фаза 11.2, задача 7) требовали пометить код использованным без гонки: `payload.update({ collection: 'promo-codes', where: { and: [{ id }, { isUsed: { equals: false } }] }, data: { isUsed: true, ... } })` — единственный `UPDATE ... WHERE` атомарен на уровне Postgres, поэтому два одновременных запроса не смогут оба «выиграть». Возвращает `{ docs, errors }` (тип `BulkOperationResult`, не одиночный документ, как у update-по-id) — пустой `docs` значит «условие `where` не совпало ни с одним документом» (код уже использован кем-то ещё). **Это снижает, а не устраняет гонку полностью** — код помечается использованным ПОСЛЕ создания заказа (иначе передумавший клиент «сжигал» бы код зря), поэтому теоретическое окно между «заказ создан» и «код помечен» остаётся; для масштаба этого проекта (бутик, не flash-sale) сочтено достаточным — как и остальные места, где строгая транзакционная защита сознательно не заводилась (например, `variant.stock` в заказе тоже не резервируется атомарно, см. `buildItems` в `order-request/route.ts` — только `isActive` проверяется, не `stock > 0`).
- **«Галерея вылезает за рамку и обрезана» на широких/асимметричных фото — не CSS-баг контейнера, а бэкенд-кроп неверного размера изображения (багфикс, сентябрь 2026).** `Gallery.tsx` уже был структурно правильным (`aspect-square`/`size-16` + `object-contain` + `bg-surface-warm` — фикс до этого не находил ни одного случая переполнения по `boundingBox()` ни на одном тестовом изображении, включая широкое 1600×600). Реальная причина в `src/lib/catalog/product.ts::toView()` — `images[].url` брался из `image.sizes.card` (`Media.ts`: `{ width: 600, height: 600, position: 'centre' }`, оба измерения заданы → sharp по умолчанию делает `fit: 'cover'`, то есть **жёсткий центр-кроп**, а не вписывание): у широкого кадра (например, фото gift box) обрезаются левый/правый края, у высокого — верх/низ. Владелец описал это как «фото вылезает за рамку» — визуально резкий обрезанный край асимметричного предмета действительно читается как «съезжает за границу», хотя технически контейнер ни на пиксель не переполнялся (проверено `boundingBox()`: идентичный `572.5×572.5` на любом изображении). Диагностировано доказательно: тестовое изображение с цветными полосами по краям (`sharp` SVG→JPEG) — в сгенерированном `card` (600×600) полосы у краёв отсутствуют, в `full` (`{ width: 1200 }`, только одно измерение → sharp всегда пропорционально масштабирует, без кропа) — присутствуют. **Фикс — чисто фронтенд, без трогания бэкенд-кропа/файлов**: `Gallery.tsx` (инлайн-просмотр и миниатюры) теперь берёт `full` вместо `card` — тот уже существовал (использовался в zoom-оверлее), просто не был подключён к основному просмотру. `ProductCard.tsx` (карточка листинга) и `GiftItemCard.tsx` этот баг не тронут намеренно (не входили в scope тикета) — те тоже читают `sizes.card`, и там та же теоретическая уязвимость для широких/асимметричных фото остаётся, если понадобится — чинить тем же приёмом.
- **Кросс-полевая обязательность в Payload (поле A обязательно в зависимости от значения поля B) — не через `required: true` (тот не умеет быть условным), а через `validate()` на поле A, читающий `data.B`.** Первое применение в проекте (фаза 11.2, задача 5: `customer.address` обязателен, только если верхнеуровневый `deliveryMethod === 'delivery'`). Ловушка — типизация: TS не может вывести типы параметров стрелочной функции `validate: (value, { data }) => ...` внутри литерала `fields: [...]` (implicit `any` на `value` и `data`, TS7006/TS7031), а generic-алиасы вида `TextFieldSingleValidation` (`Validate<string, unknown, unknown, TextField>`) фиксируют `TData = unknown` — `data.deliveryMethod` не скомпилируется. Рабочий рецепт: `import type { Validate, TextField } from 'payload'`, `import type { Order } from '@/payload-types'`, и `validate: ((value, { data }) => {...}) satisfies Validate<string, Partial<Order>, unknown, TextField>` — `satisfies` даёт контекстную типизацию параметров функции (как обычная аннотация типа) и одновременно проверяет совместимость с ожидаемой Payload-сигнатурой, без `as`-каста.
- **`ALTER TYPE ... ADD VALUE` нельзя *использовать* в той же транзакции, где значение добавлено** — весь `up()`/`down()` одного файла миграции у Payload идёт одной транзакцией, разбиение на несколько `db.execute()` внутри неё НЕ спасает (проверено — падает с `unsafe use of new value`). Если новое значение нужно тут же использовать (например, восстановить старые строковые данные при откате enum-миграции) — не инкрементальный `ADD VALUE`, а полная пересборка типа: колонка временно в `text`, данные, потом `DROP TYPE`/`CREATE TYPE` с полным списком заново и `USING`-cast (см. `20260811_202528_phase5_link_targets_pages.ts`). Инкрементальный `ADD VALUE` безопасен только если новое значение используется в ДРУГОЙ, более поздней миграции/транзакции (так и было в `20260811_090518_phase4_6_order_flow.ts`).
- **Локализованные поля внутри массивов Payload.** Запись локалей подряд (`updateGlobal` ro → ru → en) пересоздаёт строки массива и стирает подписи предыдущих локалей. Решение: после первой локали перечитать id строк и передать их в последующие записи.
- **Zod 4 и пустые ячейки CSV.** `z.preprocess(fn, z.number()).optional()` не работает — `.optional()` проверяет вход *до* препроцессора, а пустая ячейка приходит как `''`. Правильно: `z.preprocess(fn, z.number().optional())`.
- **Импорт не должен переписывать slug.** Slug у существующего товара меняется только если в файле явно есть колонка `slug` — иначе переименование в прайсе молча ломает URL и канониклы.
- **Список колонок CSV-формата продублирован текстом в шести местах, единого источника истины нет.** `src/lib/import/schema.ts` (сама схема), `detect.ts` (`KIND_LABELS`), `report.ts` (заголовочная строка отчёта), `docs/import-guide.md`, `scripts/import.ts` (текст `USAGE` для CLI), `src/components/admin/ImportForm.tsx` (подсказка под селектором локали в `/admin/catalog-import`). Реально словленный баг (фаза 8.1, задача 3): когда title убрали из формата переводов, `USAGE` в `scripts/import.ts` не поправили — CLI ещё сессию показывал устаревшее `handle,locale,title,description`. При следующем изменении набора колонок (новая опциональная колонка, переименование, формат C и т.п.) — грепать `description_ro` (или что там меняется) по всему репозиторию, не полагаться на память о том, что где упоминается.
- **`title` товара (фаза 8.1) больше не `localized: true`.** Было: три одинаковые копии на ro/ru/en (разведка перед миграцией показала 12/12 демо-товаров с идентичным title во всех локалях — «перевод» title через `demo-translations.csv`/`applyTranslations` был фиктивным дублированием, реально переводилось только description). Стало: одно общее поле на английском, description остаётся localized. Бэкфилл в `20260822_140412_phase8_1_title_not_localized.ts` берёт первую непустую локаль по приоритету ro → ru → en (не жёстко ro) — переживает и товары без ro-версии. **Ловушка на будущее:** `payload migrate:create` корректно диффит сам столбец (переносит `title`/`version_title` между `products`↔`products_locales` и `_products_v`↔`_products_v_locales`, включая btree-индекс `index:true`), но НЕ видит ручные SQL-индексы, которых нет в декларативной схеме Payload — тут это `products_locales_fts_{ro,ru,en}_idx` и `products_locales_title_trgm_idx` из `20260804_200000_search.ts`. Их пришлось дропать/пересоздавать на новом месте руками внутри той же миграции — иначе `DROP COLUMN` их бы тоже снёс (индекс зависит только от столбца, каскад не требует явного `CASCADE`), но новых на `products` никто бы не создал, и полнотекстовый поиск по названию товара тихо остался бы без индекса. Один индекс `products_title_fts_idx` с конфигом `'english'` вместо трёх локале-специфичных — title теперь всегда на английском, стемминг по ro/ru тут не нужен. `src/lib/search/fts.ts` соответственно больше не джойнит `products_locales` ради title — читает `p.title` напрямую, конкатенируя с `bl.title` бренда (тот остаётся localized).
- **Форматы A/B: description_ro/description_ru/description_en (фаза 8.1, задача 3) перекрывают одиночную description целиком, если хоть одна из трёх заполнена в заголовке файла** — обе формы одновременно не смешиваются построчно, чтобы не было двух источников истины на одно поле. Присутствие колонок определяется по ЗАГОЛОВКУ файла (`detectDescriptionLocales`, `detect.ts`), не по конкретной строке — это то, что видно в первой строке отчёта (`... (описания: ro, ru, en)`). А вот запись по локали — по каждой строке отдельно: пустая ячейка одной локали не отправляет `update` для неё, значит не затирает то, что уже переведено в базе вручную. Каждая заполненная локаль — отдельный `payload.update({locale, data:{description}})` ПОСЛЕ основного create/update (тот единственный локале-независимый вызов пишет все нелокализованные поля разом — title, variants, brand и т.д.); для нового товара id берётся из результата `payload.create()`, не из повторного `find`.
- **Payload с `fallback: true` при обычном `update` САМ проливает значение дефолтной локали в пустые локали — даже если в `data` этого поля нет вообще.** Поймано на живом импорте (фаза 8.1, задача 5): у товара было заполнено только ro-описание, ru/en — `NULL`; обычный `payload.update({locale: 'ro', data: {handle, title, variants}})` без единого упоминания `description` — и в БД ru/en внезапно получили копию ro-текста. Практическое следствие: **любую проверку «пусто ли поле в этой локали» нужно делать СТРОГО ДО основного update**, иначе после него пустых локалей уже не останется и логика «дозаполнить только пустое» не сработает вовсе (именно так молча ломалось дублирование одиночной `description` — отчёт показывал 0, писать было некуда). В `applyProducts.ts` порядок поэтому жёсткий: посчитать `singleDescriptionTargets` → основной create/update → записать дубли. Не переставлять местами.
- **Проверять «пусто ли localized-поле» через `findByID` можно только с `fallbackLocale: false`.** У проекта `fallback: true` (payload.config.ts), поэтому чтение пустой ru-версии по умолчанию вернёт ro-текст — поле выглядит заполненным, хотя в БД там `NULL`. Плюс, если поле lexical richText, недостаточно проверить «объект непустой»: пустой редактор — это тоже валидное дерево `{root: {children: [...]}}`. Проверять надо наличие непробельного `text`-узла, рекурсивно спускаясь И в `root`, И в `children` (`hasText()` в `applyProducts.ts`) — забытый `root` в первой версии дал ровно обратную ошибку: непустые описания читались как пустые, и боевой прогон затёр все три готовых перевода тестовым текстом (поймано живой проверкой до коммита, но урок дорогой).
- **Форматы A/B: колонка `images` (фаза 8.1, задача 4) — непустая ячейка ЗАМЕНЯЕТ весь список фото товара целиком, пустая ячейка (или отсутствие колонки) не трогает существующие фото вообще.** Это тот же принцип, что у description_*, но с одним отличием: если непустая ячейка перечисляет имена, из которых НИ ОДНО не нашлось в медиатеке — список фото всё равно заменяется (на пустой), а не оставляется как был. Это осознанный выбор (CSV — источник истины на весь список), не баг: проверено вживую (`docs/import-guide.md` живая проверка) отдельно от случая с частичным совпадением, где ненайденные имена просто выпадают из итогового списка, а найденные — применяются. Различать через `base.images?.length` (сырой список ДО резолва) — истинность этой проверки решает, трогать ли `data.images` вообще; `imageIds` (список ПОСЛЕ резолва, может быть короче или даже пустым) идёт в `data.images`, только если сырой список был непустым.
- **Media-загрузка ZIP-архивом (фаза 8.1, задача 4) — Buffer в памяти через `payload.create({file: {data, mimetype, name, size}})`, не `filePath`.** Тот же принцип, что уже применён к CSV-импорту (`adminCatalog.ts`) — файл не касается диска вообще, поэтому non-root-ограничение записи под `/app` в прод-контейнере (см. выше, «Non-root `nextjs`…») этот путь не задевает. `adm-zip` (чистый JS, без нативных бандлов — важно для того же образа, что уже один раз ловил `SIGSEGV` от `sharp`/libvips без `fontconfig`) читает архив тоже полностью в памяти (`new AdmZip(buffer).getEntries()`), `entry.getData()` — тоже Buffer, без временных файлов на диске.
- **`Media.imageSizes` не апскейлит — размер `full` (`width: 1200`, без `withoutEnlargement:false`) остаётся `null` в ответе API, если исходник меньше 1200px по ширине.** Пойман живьём при тестировании фото-импорта: тестовые квадраты 800×800 создались нормально (thumb/card сгенерились, оба ≤800), а `sizes.full.url` — `null`. Фронтенд это уже переживает штатно (`src/lib/catalog/product.ts:58` — `image.sizes?.full?.url ?? image.url ?? ''`, фоллбэк на оригинал), так что визуально ничего не ломается, но при отладке «почему в API `full: null`» — сначала смотреть реальный размер исходника, не искать баг в пайплайне загрузки. Ровно поэтому рекомендация клиенту в `docs/import-guide.md` — присылать квадраты **не меньше** 1200×1200.
- **`title` товара (фаза 8.1) больше не `localized: true`.** Было: три одинаковые копии на ro/ru/en (разведка перед миграцией показала 12/12 демо-товаров с идентичным title во всех локалях — «перевод» title через `demo-translations.csv`/`applyTranslations` был фиктивным дублированием, реально переводилось только description). Стало: одно общее поле на английском, description остаётся localized. Бэкфилл в `20260822_140412_phase8_1_title_not_localized.ts` берёт первую непустую локаль по приоритету ro → ru → en (не жёстко ro) — переживает и товары без ro-версии. **Ловушка на будущее:** `payload migrate:create` корректно диффит сам столбец (переносит `title`/`version_title` между `products`↔`products_locales` и `_products_v`↔`_products_v_locales`, включая btree-индекс `index:true`), но НЕ видит ручные SQL-индексы, которых нет в декларативной схеме Payload — тут это `products_locales_fts_{ro,ru,en}_idx` и `products_locales_title_trgm_idx` из `20260804_200000_search.ts`. Их пришлось дропать/пересоздавать на новом месте руками внутри той же миграции — иначе `DROP COLUMN` их бы тоже снёс (индекс зависит только от столбца, каскад не требует явного `CASCADE`), но новых на `products` никто бы не создал, и полнотекстовый поиск по названию товара тихо остался бы без индекса. Один индекс `products_title_fts_idx` с конфигом `'english'` вместо трёх локале-специфичных — title теперь всегда на английском, стемминг по ro/ru тут не нужен. `src/lib/search/fts.ts` соответственно больше не джойнит `products_locales` ради title — читает `p.title` напрямую, конкатенируя с `bl.title` бренда (тот остаётся localized).

- **Добавляя второй «продаваемый» тип товара в корзину (фаза 11.1, задача 2) — не заводи параллельный `Cart`/`Order`-механизм, расширь дискриминатором.** `CartItem`/`orderItemSchema` получили `kind: 'product' | 'gift'` и `volume` стал необязательным — этого хватило, чтобы `gift-items` прошли весь путь (корзина → заявка → CSV/email/Telegram/thank-you) без второго стора и без второй схемы. Почти всё отображение `item.volume` в проекте уже было написано с расчётом на опциональность (`item.volume ?? ''`, `item.volume ? ... : ''`) — не тронуто вообще; правки понадобились только там, где `item.volume ?? ''` стоял ВНУТРИ строкового шаблона с хардкод-суффиксом (`` `${item.volume ?? ''} ml` `` в `email.ts`) — при отсутствии объёма это печатает висячее « ml» без числа, а не пустую строку. Если добавится третий тип (третий discriminant значение) — искать именно этот паттерн (`?? '' ...суффикс`), а не полагаться на то, что «опциональность уже была».
- **`buildItems()` в `order-request/route.ts` — не единственный барьер честности цены, но он единственный для этого пути.** Когда снапшот позиции строится из нескольких коллекций (продукт/подарочный товар), проще ветвиться по явному `requested.kind`, присланному клиентом, чем пытаться угадать коллекцию перебором (`slug`/`sku` разных коллекций теоретически могут совпасть) — клиентский `kind` не даёт цену, только маршрут резолва, поэтому подделать его бессмысленно (сервер всё равно переспрашивает цену у своей коллекции).

## Роуты и API

- **Нельзя занимать `/api/<slug-коллекции>`.** Статический маршрут Next выигрывает у payload-овского `[...slug]` — `/api/orders` перекрыл REST Payload и сломал админку. Приём заявок живёт на `/api/order-request`. Правило действует для всех будущих роутов.
- **`useSelection().getSelectedIds()` не годится для bulk-действий** при выборе «все доступные» за пределами страницы — возвращает id только загруженных строк. Нужен `getQueryParams()`.
- **Сегментный `loading.tsx` ломает HTTP-статус `notFound()` ниже по дереву — реальный `404` превращается в `200`.** `loading.tsx` оборачивает всё дерево сегмента в Suspense; стриминг обязан отправить заголовки (статус `200`) до того, как содержимое разрешится, а если внутри позже вызывается `notFound()` — статус уже не переписать (проверено на dev и на `next build && next start`, воспроизводится и без Payload — чистый Next.js). Если под сегментом есть маршруты с `notFound()` (карточка товара, бренд, страница заказа по токену и т.п.) и статус важен для SEO — либо не ставить общий `loading.tsx` на этом уровне, либо переносить его глубже, в поддерево без `notFound()`. Диагностика: `curl -o /dev/null -w '%{http_code}'` на заведомо несуществующий URL — молча ловится только `curl`, в браузере разницы не видно (контент рендерится верно).
- **Next.js не подключает вложенный `not-found.tsx` к сегменту сам по себе** — только к явному `notFound()`, вызванному внутри уже совпавшего маршрута. Путь, вообще не совпавший ни с одним файлом в дереве (опечатка в адресе), уходит в дефолтный (небрендированный) 404 Next.js, минуя кастомный `[locale]/not-found.tsx`. Решение — задокументированный паттерн next-intl «catching unknown routes within a locale»: `[locale]/[...rest]/page.tsx`, вызывающий `notFound()` явно.
- **`robots.ts` внутри route group (`(frontend)`) при живом `[locale]/[...rest]` catch-all в этой сборке (Next 16.2.6 + Turbopack) отдавал 404** — запрос на `/robots.txt` неожиданно проваливался в динамический `[locale]` сегмент (лог показывал `generate-params` таймингом, типичным для `[locale]`), рендерился кастомный `not-found.tsx` вместо файла-конвенции. `sitemap.ts` в той же папке при этом работал нормально — баг асимметричный, не «route group ломает все metadata-файлы». Не разбирался до первопричины (могло быть особенностью именно этой canary-сборки) — рабочее решение: `robots.ts` вынесен на самый верх, `src/app/robots.ts` (не `src/app/(frontend)/robots.ts`), `sitemap.ts` остался в `(frontend)` без проблем. Если снова столкнёшься — сначала попробовать переместить наверх, потом уже копать глубже.
- **File-convention роуты без расширения в URL (`icon.tsx` → `/icon`, фаза 7.4) next-intl middleware по умолчанию считает обычной страницей и редиректит на `/ro/icon` (308) → 404, потому что там такого маршрута нет.** Причина понятна и точна (не как с `robots.ts` выше): матчер мидлвари `'/((?!admin|api|_next|_vercel|.*\\..*).*)'` исключает пути **с точкой** (`/robots.txt`, `/sitemap.xml` — там `.*\\..*` отрабатывает верно), но `/icon` точки не содержит — попадает под общий `.*` и обрабатывается как обычная страница, требующая локали. Перенос файла в другую папку (в отличие от `robots.ts`) тут НЕ помогает — дело не в расположении файла, а в паттерне мидлвари. Решение — добавить конкретное имя в матчер: `'/((?!admin|api|_next|_vercel|icon|apple-icon|.*\\..*).*)'` (`src/proxy.ts`). Если появится ещё один file-convention роут без точки в URL (напр. `apple-icon`, кастомный `manifest` без `.json`) — дописывать сюда же явным именем, полагаться на исключение по точке нельзя.
- **Порядок проверок в `src/proxy.ts` — не переставлять: байпас → cookie → исключения → заглушка → локали (фаза 9.2).** Каждая перестановка ломает конкретный сценарий, а не «просто менее аккуратна»: опустить проверку `?preview=` ниже заглушки — секретная ссылка сама отдаст заглушку и никогда не поставит cookie (байпас не заработает вообще, а выглядеть будет как «неверный токен»); опустить проверку cookie ниже заглушки — впущенный однажды человек снова упрётся в заглушку на следующей же странице; поднять исключения выше байпаса — `?preview=` перестанет срабатывать на служебных путях (мелочь, но ссылку владелец кидает какую попало, вплоть до `https://monflacon.md/robots.txt?preview=…`). Отдельно: **исключение для генератора OG-превью (`/{locale}/og-image`) обязательно** — превью в соцсетях собирает `facebookexternalhit`, у него нет cookie байпаса, и закрытый заглушкой генератор = не собравшееся превью в Instagram/Facebook именно тогда, когда идёт анонс. Список исключений продублирован в коде (`isMaintenanceExempt`, `src/lib/maintenance.ts`), а не оставлен на совести `config.matcher` — матчер правят по другим поводам.
- **`crypto.timingSafeEqual` из `node:crypto` в мидлвари недоступен — она идёт в edge-рантайм.** Сравнение секретов постоянного времени там делается через `crypto.subtle.digest('SHA-256', ...)` и побайтовый XOR дайджестов (`timingSafeEqual` в `src/lib/maintenance.ts`): длина дайджестов всегда одинакова, поэтому не утекает даже длина исходной строки. Тот же принцип понадобится любому будущему сравнению секретов в мидлвари (подпись вебхука, ключ предпросмотра CMS).
- **Серверные (не `NEXT_PUBLIC_`) переменные окружения мидлварь читает В РАНТАЙМЕ, а не на сборке — проверено вживую (фаза 9.2).** Прод-сборка сделана при `MAINTENANCE_MODE=0`, запущена командой `MAINTENANCE_MODE=1 pnpm start` — заглушка включилась без пересборки. Практический вывод для Coolify: переключить режим можно рестартом с новым значением переменной, полный redeploy не обязателен. **А вот `NEXT_PUBLIC_*` (соцсети на заглушке) подставляются именно на сборке** — добавить TikTok рестартом нельзя, нужен полный redeploy. Ровно та же разница, что уже ловилась с `NEXT_PUBLIC_GA_ID` (фаза 7.5).

## Кэш

- **CLI не сбрасывает кэш витрины.** `pnpm seed` и CSV-импорт идут отдельным процессом, `revalidateTag` до живого сервера не достаёт — свежие данные «не появляются». Правки из `/admin` инвалидируют кэш мгновенно; для CLI страховка — TTL 300 с (`src/lib/cache.ts`), при отладке `rm -rf .next` или `pnpm devsafe`. **При автообмене с 1С понадобится дёргать ревалидацию явно.**
- **На проде (первый CSV-импорт после деплоя) эта же страховка не самолечится так быстро, как ждёшь.** Разбирался живьём: `/catalog` показывал «0 из 0» после успешного импорта (`_status`/`minPrice`/`maxPrice`/`inStock` в БД — все корректны, проверено `psql` напрямую), а главная («Новинки») те же товары уже видела. Причина — `/catalog` был открыт/закэширован (`unstable_cache`, диск `.next/cache/fetch-cache`) ДО импорта, когда БД была пустой; `getFlaggedProducts` (главная) и `getProductCards`/`getFacetSource` (`/catalog`) — независимые `unstable_cache`-записи с разными ключами, кэшируются и протухают порознь. **Воспроизвёл и починил без единой правки кода**: чистая БД → прод-сборка (`pnpm start`) → `/catalog` (закэшировался пустым) → импорт CSV отдельным процессом → `/catalog` всё ещё пустой даже спустя >300с и два запроса подряд (TTL номинально истёк, но записи это НЕ починило само по себе за разумное время — не полагаться на «просто подождать TTL»); `rm -rf .next/cache/fetch-cache` на живом процессе без рестарта — `/catalog` сразу отдал все 12 товаров. **Рабочий фикс без доступа к файловой системе контейнера**: зайти в `/admin`, сохранить любой товар (даже без изменений) — `Products.ts`-хук `afterChange: [() => revalidateCatalog()]` живёт внутри настоящего запроса Next.js (не CLI), поэтому `revalidateTag` в нём реально срабатывает и чистит ВСЕ записи с тегом `products` сайта целиком, не только один товар. Данные при этом не трогать — они уже верны, чинить нечего, кроме кэша. См. `docs/import-guide.md`.
- **`unstable_cache` переживает перезапуск dev-сервера** — лежит в `.next`.
- **`revalidateTag` после правки глобала не всегда успевает к первому же запросу.** Следующий HTTP-запрос иногда ловит ещё не пересчитанный кэш, второй уже свежий. Тесты делают «прогрев»: два запроса подряд, читается результат второго.
- **Фронтовый layout — `force-dynamic`.** Прод-сборка падала: `generateStaticParams` ходил в БД, которой при `docker build` нет (обёрнут в `staticParamsOrEmpty`), а шапка/футер тянут данные из Payload и роняли пререндер с «missing secret key». Данные всё равно в `unstable_cache`. К полному кэшу маршрутов вернуться в фазе 7.
- **`staticParamsOrEmpty` нужен на КАЖДОМ маршруте, который ходит в БД на этапе сборки — не только на `generateStaticParams`.** Фаза 7.3 добавила `src/app/(frontend)/sitemap.ts` (тоже пререндерится статикой, `revalidate = 3600`) и забыла обернуть его запросы тем же паттерном — на `docker build` без поднятой БД (или с БД, где ещё не накатаны миграции — `relation "brands" does not exist`, не только `ECONNREFUSED`) `Export encountered an error on /(frontend)/sitemap.xml/route` ронял всю сборку. Почищено в фазе 8.х: `loadDynamicEntries()` в `sitemap.ts` обёрнут в `staticParamsOrEmpty`, статические записи (`/`, `/catalog`, `/brands` × 3 локали) собираются отдельно и без БД, попадают в sitemap всегда. Проверено тем же способом, что и остальные маршруты: `docker compose -f docker-compose.dev.yml stop postgres` → `pnpm build` (раньше падал, теперь `exit 0`, sitemap содержит 9 статических `<url>` вместо обычных 78) → `start postgres` → повторный `pnpm build` (снова `exit 0`, все 78). **Если появится ещё один file-convention роут с запросом к Payload на этапе сборки (`opengraph-image.tsx` со списком, ещё один `sitemap`-подобный файл и т.п.) — сразу оборачивать в `staticParamsOrEmpty`, не дожидаться падения прод-сборки.**
- **`Cache-Control`, выставленный на ответе `NextResponse.rewrite()`, в dev-режиме затирается Next'ом и виден только в прод-сборке (фаза 9.2).** `no-store, no-cache, must-revalidate, max-age=0` со стороны мидлвари в `pnpm dev` приходил к клиенту как `no-cache, must-revalidate` — то есть без `no-store`, ровно той директивы, ради которой всё и ставилось. В `pnpm build && pnpm start` заголовок доходит целиком. **Заголовки кэширования, поставленные мидлварью, проверять только на прод-сборке** — в деве проверка тестирует не тот код.
- **Заглушка «сайт в разработке» обязана отдаваться с `no-store`, иначе Cloudflare закэширует её на edge (фаза 9.2).** Прод стоит за Cloudflare с оранжевым облаком; заглушка отдаётся статусом 200 на КАЖДОМ URL сайта, поэтому один закэшированный ответ переживёт снятие режима, и часть посетителей будет видеть «сайт в разработке» ещё долго после запуска. Заголовок ставится в `src/proxy.ts` на ответ rewrite'а. Если при снятии режима кто-то всё же видит заглушку — первым делом Purge Cache в Cloudflare, а не поиск бага в коде.

## Dev-окружение

- **Dev-сервер не всегда убивается.** `lsof -ti:3000` тут пусто, `pkill -f "next dev"` убивает собственный шелл — старый процесс продолжает отвечать, и проверки идут против прежнего кода. Рабочий способ: `ps -eo pid,args | grep next-server` → `kill <pid>`. Next честно пишет в лог «Another next dev server is already running» — смотреть первые строки лога.
- **`pnpm import` перехватывается самим pnpm.** Рабочий вызов — `pnpm run import <файл>` (есть алиас `import:csv`).
- **Dev по LAN-IP требует `allowedDevOrigins`** в next.config, иначе страница отдаётся, но клиентские островки не гидрируются вовсе (HMR-вебсокет `ERR_INVALID_HTTP_RESPONSE`). Сейчас прописан `10.221.66.166` (Windows-сторона); меняется через `DEV_ORIGINS=<ip> pnpm dev`. У WSL свой адрес. На прод не влияет.
- **`ORDERS_RATE_LIMIT=5` (дефолт) не хватает самому `check-orders.mjs`.** Поднимать на ОБЕИХ сторонах на время прогона и возвращать дефолт после: `ORDERS_RATE_LIMIT=30 pnpm dev` + `ORDERS_RATE_LIMIT=30 node scripts/check-orders.mjs`. Счётчик живёт в памяти процесса — между прогонами сервер перезапускать. Постоянно поднятым в `.env` не держать: локальный дефолт должен оставаться прод-реалистичным.
- **В dev клик до окончания гидрации теряется** (холодная компиляция, не баг корзины) — проверки жмут кнопку до появления записи в localStorage.
- **`curl -I` (HEAD) на медиа-роут Payload (`/api/media/file/...`) отдаёт 404, хотя тот же URL через `curl` без `-I` (GET) — 200.** Потратил время на ложный след при отладке производительности (фаза 7.4), решив что файл/запись в БД пропали. Payload-роут раздачи файлов, похоже, не поддерживает HEAD корректно. Для диагностики «отдаётся ли медиафайл» — всегда обычный GET (`curl -s -o /dev/null -w '%{http_code}'`), не `-I`.
- **`pnpm start` при `output: 'standalone'` в `next.config.ts` печатает предупреждение «does not work with standalone configuration», но фактически исправно поднимает сервер и раздаёт код + локальные медиафайлы Payload — годится для локального прогона Lighthouse/прод-проверок.** Настоящий `node .next/standalone/server.js` рассчитан на Docker-раскладку из `Dockerfile` (рядом копируются `public/` и `.next/static`, медиа — из S3/R2, не с диска) — при прогоне standalone-сервера локально без такой раскладки и без доступа к дев-`media/` каталогу отдача изображений ломается (проверено — `/api/media/file/...` стабильно 404 через standalone-точку входа, тогда как `pnpm start` те же файлы отдаёт нормально). Для локальных прод-подобных проверок (Lighthouse и т.п.) — `pnpm build && pnpm start`, а не `node .next/standalone/server.js`; последний тестировать реалистично только через фактическую Docker-сборку (фаза 9+).
- **`npx lighthouse` из WSL создаёт временный chrome user-data-dir с буквальным именем `C:\Users\Admin\AppData\Local\lighthouse.<pid>` прямо в текущей рабочей директории** (chrome-launcher, похоже, детектит Windows-путь по какой-то переменной окружения WSL и не эскейпит его как единый Linux-каталог с обратными слэшами в имени). Не подчищается сам после прогона. После любого `npx lighthouse ...` — проверить `git status`/`ls`, снести `rm -rf -- C:*` из корня проекта.
- **`ps`/`pkill` не различают `next dev` и `next start` по имени процесса — оба показывают `next-server (v16.2.6)`.** Перед `kill` смотреть не имя, а аргументы родителя: `ps -eo pid,ppid,args`, найти `next dev` или `next start` в цепочке `ppid`, и уже потом гасить весь куст pid'ов (sh → cross-env → next → next-server), не только сам `next-server`. Спутать порты/режимы легко, если оба сервера подняты одновременно (дев на 3000 для Playwright, прод на другом порту для Lighthouse/нагрузочных замеров, фаза 8.3) — сначала `ss -ltnp | grep <порт>`, чтобы понять, какой pid слушает нужный порт, только потом `kill`.
- **`tests/e2e` через `@playwright/test` с параллельными воркерами (дефолт — по числу ядер) гоняет несколько браузерных контекстов ОДНОВРЕМЕННО против ОДНОГО общего dev-сервера** (`webServer.reuseExistingServer: true`) — при 3 воркерах клиентская RSC-навигация (`router.push`) под турбопак-компиляцией стала ловить гонки: клик по кнопке отправки формы реально доходил до сервера (заказ создавался), но `page.waitForURL()` на переход `/cart → /thank-you` не успевал за 15–20с и тест падал таймаутом, хотя функционально всё сработало. Другие тесты в это же время дублировали клики по чекбоксам/кнопкам объёма (см. пункт про гидрацию ниже), тоже пытаясь компенсировать несуществующую проблему повторным кликом — тем самым иногда попадая по уже задизейбленной кнопке. **Решение для этого проекта:** `playwright.config.ts` → `workers: 1` (не только на CI). Три полных прогона `pnpm test:e2e` стабильно зелёные при последовательном выполнении; при параллельных воркерах — флаки то в одном файле, то в другом, без постоянного виновника.
- **Гидрационная гонка (см. «В dev клик до окончания гидрации теряется» выше) не ограничена корзиной** — тот же паттерн потерянного первого клика ловился и на чекбоксе фасета каталога, и на кнопке переключения объёма, и на кнопке отправки формы заявки при живом (даже последовательном, `workers: 1`) прогоне E2E сразу после навигации на страницу. Общее решение в `tests/e2e/*.spec.ts` — не проверять эффект сразу после одного клика, а оборачивать «клик + проверка эффекта» в `expect(async () => {...}).toPass({ timeout: 10000 })`: если клик потерян, следующая итерация клика повторит его, если клик дошёл — проверка сразу пройдёт и цикл не продолжится. Не годится для кнопок, которые после первого успешного клика становятся `disabled` (форма заявки после сабмита) — там достаточно одного клика с длинным `waitForURL`, повторный клик по задизейбленной кнопке только тратит бюджет таймаута.
- **`PAGE_SIZE=24` (`src/lib/catalog/searchParams.ts`) делает проверку «фильтр уменьшил число карточек на странице» ненадёжной при каталоге больше ~24 товаров на фасет.** На демо-данных (12 товаров) фильтр всегда сокращал видимую выдачу — на нагрузочном объёме (132 товара, ~44 на бренд, фаза 8.3) первая страница фильтрованной и нефильтрованной выдачи обе показывают ровно 24 карточки: видимая дельта — 0, хотя `totalDocs` за кадром меняется верно (132 → 44, проверено через `/api/products?...&limit=0`). Для проверки фильтрации на объёме — сравнивать `totalDocs` из REST, не количество `<article>` на странице. `scripts/check-catalog.mjs` (фаза 3, на демо-данных) и новые `tests/e2e/catalog-filters.e2e.spec.ts` (фаза 8, пишет через API) с этим не сталкиваются — риск актуален только если кто-то будет писать новую проверку фильтров на реальном объёме товаров через видимый счёт карточек.

## UI, токены, React

- **`tailwind-merge` молча съедает брендовые цвета.** Кастомные размеры вида `text-label`/`text-body` он относит к группе `text-color` и вычищает соседний `text-cream` (CTA рендерился navy на navy). `src/lib/utils.ts` переведён на `extendTailwindMerge` с явным перечислением токенов по группам. **Правило: новый токен в `tokens.css` из неоднозначного неймспейса → добавить его в списки в `utils.ts`.**
- **Хардкод цветов/радиусов/шрифтов запрещён** — только токены `src/styles/tokens.css`, по `docs/BRAND.md`.
- **Правило react-hooks в Next 16 запрещает синхронный `setState` в эффекте** и чтение ref во время рендера. Приёмы, которые сработали: `useSyncExternalStore` (гидрация корзины, sticky-скролл, а также `ConsentBanner.tsx`/`GoogleAnalytics.tsx` фазы 7 — `getServerSnapshot` возвращает `false`, что совпадает с прежним начальным `useState(false)`, а `subscribe` — та же функция `onConsentChange`, что уже была), перенос на следующий тик `setTimeout(..., 0)` (баннер, восстановление URL после шторки), вычисление состояния из пути вместо сброса эффектом.
- **Значение override для ссылок вводится БЕЗ префикса локали** (`/catalog?flags=isNew`, не `/ru/catalog?...`) — `<Link>` из `@/i18n/navigation` добавляет префикс сама, иначе он удваивается.
- **Цвета `--color-status-*` — служебные, вне палитры BRAND.md** (как `--color-danger`), подобраны по смыслу. Если владелец захочет другую логику цветов статусов — правится в одном месте.
- **`src/app/(payload)/layout.tsx` помечен Payload как «не редактировать»,** но импорт `tokens.css` туда добавлен осознанно — обычные dev-команды его не трогают. После добавления новых admin-компонентов обязателен `pnpm generate:importmap`, иначе админка падает на «PayloadComponent not found in importMap».
- **Кастомные top-level admin-views (`admin.components.views`, регистрация нового пути вроде `/admin/<путь>`) Payload НЕ оборачивает в штатный layout (шапка/сайдбар/тема) сам** — в отличие от экранов коллекций/дашборда/аккаунта. Причина — в рендер-пайплайне (`@payloadcms/next/dist/views/Root/getRouteData.js`) такие пути матчатся отдельным catch-all'ом (`getCustomViewByRoute`) уже ПОСЛЕ основного `switch` по известным типам view, и в этой ветке `templateType` не проставляется вовсе — рендер уходит голым `Fragment`'ом без `DefaultTemplate`/`MinimalTemplate`. Поймано вживую скриншотом (фаза 8.1, задача 2): первая версия экрана импорта CSV рендерилась вообще без единого стиля Payload — обычный браузерный serif-дефолт, ни хедера, ни навигации. Решение — оборачивать компонент `DefaultTemplate` из `@payloadcms/next/templates` вручную, тем же набором пропсов, каким сам Payload оборачивает штатные экраны (см. `node_modules/@payloadcms/next/dist/views/NotFound/index.js` как образец, и `src/components/admin/ImportView.tsx` в этом проекте).
- **Sticky-шапка, меняющая высоту по порогу скролла, без гистерезиса = вечный автоскролл.** Шапка `sticky` остаётся в потоке документа: сжатие уменьшает высоту контента ВЫШЕ текущей позиции, браузерный scroll anchoring компенсирует это сдвигом `scrollY`, порог пересекается обратно — и цикл идёт каждый кадр (страница «сама скроллит» вверх-вниз, CPU в потолок). Воспроизведено замером на фазе 9.1: со старым `useScrolled(40)` парковка скролла на 42–46px давала самопроизвольное гуляние 37–45px. **Правило: любой порог, который управляет размером элемента в потоке, делать с мёртвой зоной заведомо шире изменения размера** (`src/lib/useScrolled.ts`, ±24px при дельте шапки ~14px).
- **Блокировка `body { overflow: hidden }` при открытии оверлея двигает всю страницу по ширине** — исчезает полоса прокрутки. Лечится один раз глобально: `scrollbar-gutter: stable` на `html` (`styles.css`), а не компенсацией padding'ом в каждом компоненте. Иначе любой новый дровер/модалка снова принесёт layout shift.
- **Точку входа, привязанную к индексу CMS-массива, ломает не код, а контент.** Ссылка «Отследить заказ» жила внутри `columns.map()` футера под `index === 1` — стоило владельцу очистить `footerColumns`, и вход в отслеживание заказа исчез с прода целиком, при полностью рабочем роуте. **Системные ссылки (не редакторский контент) рендерить вне циклов по данным CMS.**
- **Статический сегмент внутри маршрута с соседним динамическим `[slug]` побеждает его сам, без доп. настройки (фаза 11.1).** `src/app/(frontend)/[locale]/catalog/body-care/page.tsx` (новая страница «Уход за телом») соседствует с `src/app/(frontend)/[locale]/catalog/[category]/page.tsx` — Next.js матчит `/catalog/body-care` на статическую папку, а не проваливает запрос в `[category]` с `category: 'body-care'` (что дало бы 404, так как такой категории нет в таксономии). Полезно помнить при добавлении новых фиксированных разделов рядом с существующими динамическими каталожными маршрутами — специальный приоритет прописывать не нужно, это поведение файловой маршрутизации Next.js по умолчанию.
- **`user` не приходит в пропсы кастомного top-level view напрямую** — в отличие от слотов вроде `afterNavLinks`/`beforeDashboard` (там он есть через `ServerProps`), у top-level view он лежит вложенным в `initPageResult.req.user`. Деструктуризация `{ user }` из пропсов такого компонента молча даёт `undefined` — экран решит, что залогинен кто угодно кроме админа, и покажет отказ в доступе даже настоящему admin. Ловится только живой пробой под обеими ролями, «выглядит правильно» в коде не гарантирует ничего (фаза 8.1, задача 2, `ImportView.tsx`).

## Синхронизация кода и доков

- **Новая цель ссылки — не только в код.** Появился новый маршрут или пункт навигации → он должен попасть в `LINK_TARGETS` (`src/lib/links.ts`), в `docs/PLAN.md` (раздел своей фазы), при необходимости в `docs/PROMPTS.md`, и строками во все три `messages/*.json`. Иначе цель живёт только в коде, а доки расходятся с реальностью.
- **Готовая страница без точки входа = не сделано.** Так вышло с отслеживанием заказа в 4.7: `/order/[token]` и поиск номер+телефон работали, но попасть на них из интерфейса было нельзя. Критерий приёмки маршрута — не только «страница отвечает 200», но и «на неё есть кликабельный путь».

## Самопроверка и тесты

- **Тесты не должны опираться на текст цены на карточке.** С «вариантом B» бейджа отображаемая цена не обязана быть минимальной — сортировка на сервере идёт по настоящему `minPrice`. Порядок сверяется со slug'ами и `minPrice` из отдельного REST-запроса к `/api/products`.
- **Селекторы в тестах должны быть узкими.** «Первый `<span>` в карточке» сломался, когда появился бейдж скидки. Брать по классу (`.tracking-label` — бренд, `.tracking-display` — бейдж).
- **`innerText` в Chromium отдаёт текст уже с `text-transform: uppercase`** → сравнение строк регистронезависимое. И «нет в наличии» содержит «в наличии» как подстроку — читать текст самой плашки, а не всей карточки.
- **Playwright не подхватывает `prefers-color-scheme` в админке Payload** — тема резолвится в JS после гидратации. Форсировать `data-theme` через `page.evaluate`.
- **Гонки проверяются искусственной задержкой, а не на глаз:** `page.route('**/api/...', ...)` с задержкой перед `route.continue()` + поллинг DOM каждые 60–80 мс. Методику стоит валидировать откатом на старый код — тест обязан поймать баг до правки, иначе он тестирует вхолостую.
- **`.toPass()` вокруг клика по кнопке, которая исчезает от собственного клика, зацикливается.** Так вышло со «сбросить всё»: после сброса строка активных фильтров пропадает вместе с кнопкой, повторная попытка виснет на отсутствующем локаторе, и тест падает, хотя действие давно сработало. Внутри `.toPass()` жать по условию (`if (await button.isVisible())`), а проверять результат — отдельным `expect` после.
- **Тестовые заявки чистить до одной после прогона** — накапливаются десятками. Одна оставляется как образец для владельца.
- **Отладочное состояние из curl-экспериментов течёт в БД** и даёт ложные провалы. Сценарии проверок должны сами обнулять поля вроде `linkTargetOverride` на старте.
